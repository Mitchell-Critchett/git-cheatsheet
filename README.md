## 🧠 Основные понятия

*   **Репозиторий (Repository)** — каталог, в котором Git отслеживает изменения файлов.
*   **Рабочая директория (Working Directory)** — текущие файлы проекта на вашем компьютере.
*   **Коммит (Commit)** — снимок состояния проекта, сохраняющий изменения с уникальным ID.
*   **Main / Master** — основная ветка проекта.
*   **Удаленный репозиторий (Remote)** — копия проекта, хранящаяся на сервере (например, GitHub).

## 🛠 Настройка и инициализация проекта

### Глобальная настройка Git (выполняется один раз)
```bash
git config --global user.name "Ваше Имя"
git config --global user.email "your_email@example.com"
```

### Создание нового локального репозитория
```bash
cd /путь/к/папке/проекта
git init
```

### Клонирование существующего репозитория из сети
```bash
git clone https://github.com
```

## 💻 Работа с коммитами

### Проверка текущего статуса файлов
```bash
git status
```

### Подготовка файлов (добавление в индекс)
```bash
git add file.txt       # Подготовить конкретный файл
git add .              # Подготовить все измененные и новые файлы
```

### Фиксация изменений (создание коммита)
```bash
git commit -m "Понятное описание сделанных изменений"
```

### Просмотр истории изменений
```bash
git log                # Полный лог со всеми деталями
```

## 🔑 Настройка авторизации по SSH

Связка работает на основе двух ключей: **приватного** (остается на ПК) и **публичного** (отправляется на GitHub). Это избавляет от необходимости вводить пароли и токены.

### 1. Генерация пары ключей
Выполните команду в терминале (нажимайте **Enter** на все всплывающие вопросы):
```bash
ssh-keygen -t ed25519 -C "your_email@example.com"
```

### 2. Добавление ключа в SSH-агент
```bash
eval "\$(ssh-agent -s)"       # Запуск агента в фоне
ssh-add ~/.ssh/id_ed25519    # Добавление приватного ключа
```

### 3. Добавление публичного ключа на GitHub
1. Выведите публичный ключ на экран и скопируйте его (весь текст от `ssh-ed25519` до вашего email):
   ```bash
   cat ~/.ssh/id_ed25519.pub
   ```
2. Перейдите на GitHub: **Settings** -> **SSH and GPG keys** -> **New SSH key**.
3. Вставьте ключ в поле **Key**, укажите любое название в **Title** и нажмите **Add SSH key**.

### 4. Проверка связи
```bash
ssh -T git@github.com
```
*Если появится запрос на подтверждение, введите `yes`. Вы должны увидеть приветственное сообщение со своим никнеймом.*

### 5. Привязка репозитория по SSH
При создании репозитория копируйте ссылку во вкладке **SSH** (формат: `git@github.com:...`).

```bash
# Для нового проекта:
git remote add origin git@github.com:имя_пользователя/имя_репозитория.git

# Для перехода с HTTPS на SSH в старом проекте:
git remote set-url origin git@github.com:имя_пользователя/имя_репозитория.git
```


## Отправка локального проекта на GitHub
1. Создайте пустой репозиторий на GitHub (кнопка **New** на главной странице).
2. Скопируйте предоставленную `https://` ссылку на репозиторий.
3. Откройте терминал в папке своего локального проекта и свяжите репозитории:

```bash
# 1. Привязываем удаленный репозиторий и называем его "origin"
git remote add origin https://github.com

# 2. Переименовываем текущую ветку в main (стандарт GitHub)
git branch -M main

# 3. Отправляем файлы в удаленный репозиторий
git push -u origin main
```

При первом `git push` терминал попросит ввести `Username` (ваш ник на GitHub) и `Password` (сюда нужно вставить ваш скопированный **Personal Access Token**).


# Хеширование в Git

**Хеширование** — это процесс преобразования данных о коммите в уникальную строку, которая служит **главным идентификатором коммита**.

Git объединяет информацию о коммите (автор, дата, содержимое файлов и ссылка на родительский коммит) и преобразует её с помощью алгоритма **SHA-1**.

### Ключевые свойства хеша
* **Состав:** Строка длиной **40 символов**, состоящая из цифр `0–9` и латинских букв `A–F`.
* **Постоянство:** Для одного и того же набора данных результат всегда гарантированно одинаковый.
* **Чувствительность:** Изменение даже одного символа в исходных данных полностью меняет итоговый хеш.

### Как Git использует хеши
* **Идентификация:** Git хранит таблицу соответствий `хеш` \(\rightarrow\) `информация о коммите`. Зная хеш, можно восстановить автора, дату и содержимое файлов.
* **Управление:** Хеши передаются в качестве параметров в Git-команды, чтобы указать, с каким именно коммитом нужно выполнить действие.
* **Хранение:** Все хеши и служебные данные сохраняются в скрытой папке `.git` внутри репозитория проекта.


# Просмотр истории коммитов (`git log`)

Для просмотра истории коммитов в Git используется команда `git log`. Она позволяет находить нужные изменения и получать хеши для управления ими.

### Полный лог (`git log`)
Отображает подробную информацию о каждом коммите, которая состоит из следующих элементов:
* **Хеш коммита** — уникальная строка из цифр и букв после слова `commit`.
* **Author** — имя автора и его электронная почта.
* **Date** — точная дата и время создания коммита.
* **Сообщение** — комментарий автора к коммиту.

### Сокращённый лог (`git log --oneline`)
Используется для быстрой навигации по большой истории (сотни и тысячи коммитов). 
* Выводит каждый коммит **одной строкой**.
* Содержит только **сокращённый хеш** (первые несколько символов) и комментарий.

### Ключевые особенности
* **Сокращённый хеш** можно использовать в Git-командах точно так же, как и полный. Git автоматически подбирает его длину так, чтобы она оставалась уникальной внутри репозитория.
* **Выход из режима просмотра:** Если лог не закрылся автоматически, нажмите клавишу **`Q`** (в английской раскладке клавиатуры).


# Указатель HEAD в Git

**HEAD** — это служебный указатель (ссылка), который всегда указывает на **самый свежий коммит** в вашей текущей ветке. 

Сам файл `HEAD` находится внутри скрытой папки `.git`.

### Как это работает изнутри
1. `HEAD` ссылается не напрямую на коммит, а на файл текущей ветки (например, `refs/heads/master`).
2. В файле ветки хранится хеш самого последнего коммита.
3. Когда вы делаете новый коммит:
   * Git записывает свежий хеш в файл ветки.
   * `HEAD` автоматически начинает указывать на этот новый коммит.

### Использование на практике
* **В логах:** При вызове `git log` метка `(HEAD -> master)` наглядно показывает, где вы сейчас находитесь и какой коммит является последним.
* **В командах:** Слово `HEAD` можно использовать как **синоним хеша последнего коммита**. В любых Git-командах (например, `git diff` или `git rebase`) вместо ввода 40-значного кода можно просто написать `HEAD`.


# Статусы файлов в Git и команда `git status`

Команда **`git status`** — это главный инструмент для проверки текущего состояния файлов в вашем рабочем каталоге и репозитории. Она показывает, какие файлы были изменены, добавлены или подготовлены к коммиту.

### 4 основных статуса файлов в Git

Все файлы в проекте всегда находятся в одном из двух глобальных состояний: **Untracked** (неотслеживаемые) или **Tracked** (отслеживаемые). Отслеживаемые файлы, в свою очередь, делятся еще на три статуса.

#### 1. Untracked (Неотслеживаемые)
* **Что значит:** Новые файлы, которые вы только что создали. Git о них еще ничего не знает и не следит за их изменениями.
* **В `git status`:** Отображаются в секции `Untracked files` (обычно подсвечены красным).

#### 2. Modified (Изменённые)
* **Что значит:** Файлы, которые Git уже отслеживал (они были в прошлых коммитах), но в которые вы внесли свежие изменения с момента последнего коммита.
* **В `git status`:** Отображаются в секции `Changes not staged for commit` (красный цвет).

#### 3. Staged (Подготовленные / Индексированные)
* **Что значит:** Измененные или новые файлы, которые вы добавили в "зону ожидания" (индекс) командой `git add`. Именно эти изменения попадут в следующий коммит.
* **В `git status`:** Отображаются в секции `Changes to be committed` (зеленый цвет).

#### 4. Unmodified (Неизмененные)
* **Что значит:** Файлы, которые не менялись со времени последнего коммита. 
* **В `git status`:** Они вообще **не отображаются**, так как Git фиксирует только изменения. Если все файлы в этом статусе, `git status` напишет: *"nothing to commit, working tree clean"*.

---

### Шпаргалка по командам перемещения между статусами

* `git add <имя_файла>` — переводит файл из **Untracked** или **Modified** в статус **Staged**.
* `git commit -m "сообщение"` — сохраняет все файлы из статуса **Staged** в историю. После этого их статус возвращается к **Unmodified**.
* `git restore --staged <имя_файла>` — убирает файл из зоны подготовки (**Staged** обратно в **Modified**), не стирая ваш код.

### 💡 Полезный лайфхак
Если у вас много файлов и вывод `git status` занимает весь экран, используйте компактный режим:
```bash
git status -s
```
* `??` — Untracked (новый файл)
* ` M` — Modified (изменен в рабочей директории, красный)
* `M ` — Staged (изменение подготовлено к коммиту, зеленое)
